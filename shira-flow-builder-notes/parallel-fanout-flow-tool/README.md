# Паралелен фен-аут: flow tool с Parallel Context и return bridge

Дата: 2026-08-29

## 1. Каква беше задачата

Потребителят пита няколко неща в едно изречение. Искахме те да се обработят **едновременно**,
а не едно след друго, и главният агент да върне **един свързан отговор**.

Крайният дизайн:

~~~text
потребител (5 въпроса в едно изречение)
  ↓
AgentOne (agent-two)
  ↓ SYSTEM CALL: Multi Answer  {"questions":[...]}
MultiAnswer.flow
  ↓ setup.js         улавя моста към главния агент + строи dictionary.items
  ↓ Parallel Context  Worker-Start × N, ЕДНОВРЕМЕННО
  │    ├─ клонинг 1 → worker-agent → tool → dictionary.answer
  │    ├─ клонинг 2 → …
  │    └─ клонинг N → …
  ↓ returnToMain.js  чете items (вече с answer) → push към главния агент
AgentOne
  ↓ един свързан отговор
потребител
~~~

## 2. Защо Parallel Context, а не Parallel Flows

Това е първото решение и то е принудително:

| | Parallel Flows (`parallelInNode`) | Parallel Context (`parallelContextNode`) |
|---|---|---|
| Брой клонове | **фиксиран при построяване** — колкото Flow Pointer-а на `wait` | **динамичен** — колкото елемента има масивът |
| Dictionary на клона | празен, изолиран | **seed-нат от елемента** |
| Връщане на резултат | нищо не се слива; само през канали | **целият краен dictionary се слива обратно в елемента** |

При N въпроса, което е различно всеки път, Parallel Flows е неприложим. Работи само Parallel Context.

## 3. Агентът НЕ може да се разклони сам

Engine-ът изпълнява **само първия** `<SYSTEM CALL>` блок на кръг. Дори моделът да излъчи осем,
тръгва един. Затова паралелността не може да живее в tool loop-а на агента — тя трябва да е
**в graph-а**. Това е централната архитектурна мисъл: оркестрацията се мести от агента във флоуа.

## 4. Трите неща, които правят конструкцията стабилна

### 4.1 Мостът се улавя в ПЪРВИЯ node

(Корекция 2026-09-12.) `toolOptions` всъщност оцелява вложения tool loop при референтните клиенти
(flow-engine-ът копира options по continuation nodes в същия flow; клиентът re-seed-ва всеки nodeTask на
`toolFlow` bundle от `flow.options`) — но **липсва** в Run Flow / Parallel под-flow, spawn-нат отвътре на
tool-а, и при custom client без re-seed. Затова `setup.js` го записва като защитен мост:

~~~js
dictionary.bridge = {
    mainAgentId: toolOptions.toolContext.agentId,
    mainSession: toolOptions.agentNode.flowContext.sessionId
};
~~~

`returnToMain.js` чете **само** този мост и нарочно не докосва `toolOptions`.

Важно: редът на операторите **не** пази моста. При throw dictionary промените се отменят **изцяло**
(включително мостът), така че `setup.js` трябва да **завърши чисто** — валидира, push-ва корекция,
`return` — и никога да не хвърля, след като е записал моста.

### 4.2 Всеки клонинг seed-ва СВОЯ агент със СВОЯТА сесия

Agent node не получава вход по реброто — чете най-новото user съобщение за своя `agentId`.
Вътре в клонинга:

~~~js
Agent.setRootAgentPrompt('worker-agent', {
    prompt: dictionary.q,
    sessionID: flowContext.sessionId,   // сесията на ТОЗИ клонинг
    requestID: Tools.generateUUID()
});
~~~

Петте клонинга въртят **един и същ** `agentId` едновременно. Това е безопасно само защото
резолюцията на trigger-а е session-scoped — точно механизмът зад стария бъг „3 от 4 клонинга
получиха чужд trigger".

### 4.3 Отговорите изобщо не минават през agent state

Agent node-ът е с `agentResponse: true` + `agentResponseProperty: "answer"`, тоест пише директно
в dictionary-то на клонинга. Parallel Context го слива в `items[i]`.

**Това е най-важното опростяване.** Каналите са най-коварната част от платформата (per-agent
четенията са само `root`, отговорът наследява канала на trigger-а, drain-овете изтриват). Като
пишем в dictionary, цялото това минно поле отпада — нула cross-session четения на agent state.

## 5. Какво избягахме нарочно

- **Няма Condition node.** При невалиден вход `setup.js` оставя празен масив; Parallel Context
  при празна колекция просто продължава към Out, а `returnToMain` връща корекция. По-малко възли
  и не се опира на gotcha C8 (deploy компилаторът, който бърка `true`/`false` с `next_1`/`next_2`).
- **Няма отделен агент-разделител.** Главният агент сам вади въпросите в `!*context`. Спестява
  цяло LLM извикване.
- **Елементите са обекти** — `[{q:"…"}]`, не `["…"]`. Не-обект се заменя с `{}` и клонингът тръгва празен.
- **`assignTo` е попълнено, но не се чете от engine-а.** Резултатите се вземат от самата колекция.

## 6. ИЗМЕРВАНЕ: паралелно се оказа ПО-БАВНО

Това е най-важният резултат в тази бележка, и той е отрицателен.

Пет въпроса, всеки с по един бърз tool, `gemini-2.5-pro`, по три пускания:

| | пуск 1 | пуск 2 | пуск 3 | средно | токени |
|---|---|---|---|---|---|
| Паралелно (Multi Answer) | 32s | 28s | 28s | **~29s** | 11845 in / 714 out |
| Последователно | 25s | 27s | 23s | **~25s** | 11123 in / 468 out |

**Паралелният фен-аут е ~15% по-бавен и по-скъп при това натоварване.**

Причината е в броя LLM извиквания, не в HTTP-то:

- последователно: ~6 кръга на главния агент;
- паралелно: ~13 — три на главния плюс по два на всеки от петте работника (един да извика tool-а,
  един да формулира отговора).

Конкурентността печели само когато работата по **един елемент** доминира над разноските по
разклоняването. Тук всеки въпрос е една бърза заявка и кратък кръг, така че оркестрацията струва
повече, отколкото спестява.

### Кога фен-аутът СИ СТРУВА

- всеки елемент изисква **многокръгов tool loop** (2–3 извиквания на въпрос);
- външното API е **бавно** (секунди на заявка);
- елементите са **много повече** (10–20+), където последователното време расте линейно,
  а паралелното остава ~плоско;
- обработката на елемент е тежка сама по себе си (обобщаване на дълъг текст, верига от разсъждения).

### Как да се ускори, ако все пак трябва

- махнете втория кръг на работника — нека tool-ът връща вече формулиран текст;
- по-евтин/бърз модел за работниците (haiku / flash), скъп само за съчинителя;
- пропускайте фен-аута под праг: при 2–3 въпроса викайте tool-овете направо.

## 7. Дефект, който трейсът хвана

При първото пускане работник №2 получи „Колко е часът в Ню Йорк?" и извика **Place Lookup**
вместо Current Time — върна координати.

Причина: в промпта на работника tool-овете бяха изредени само с име и форма на контекста,
**без описание кога се ползва кой**. Главният агент имаше пълни описания, работникът — не.

Поправка: описание „use for…" на всеки ред плюс изрично правило:

> A place name in the question tells you WHICH place — the question itself tells you WHAT is being
> asked about it. "What time is it in New York" is a time question, not a location question.

След поправката работникът избра Current Time.

**Странично наблюдение:** главният агент сам забеляза, че един от петте отговора не отговаря на
въпроса, и извика Current Time допълнително. Самопоправянето работи и на ниво съчинител, не само
в tool-а.

## 8. Останал недостатък

Част от работниците отговарят на **английски**, въпреки изричната инструкция да пишат на езика на
въпроса. Съчинителят ги превежда, така че потребителят вижда чист български — но се харчат токени
за превод. Ако пречи: подавайте езика като поле в елемента (`{q:"…", lang:"bg"}`) вместо да
разчитате на модела да го улови.

## 10. Универсален шаблон

~~~text
Главен агент
  ↓ извиква Flow Tool с масив елементи
Setup Script
  - улови outer agentId + session в dictionary.bridge   ← ПЪРВИЯТ оператор
  - валидирай; при проблем остави празен масив
  - dictionary.items = [{…}, {…}]                        ← обекти, не скалари
  ↓
Parallel Context  (contextCollection = dictionary.items, pipe = Worker-Start)
  клонинг:
    - seed на агента със СВОЯТА flowContext.sessionId
    - Agent node с agentResponse → dictionary.answer     ← без канали
  ↓ (Out изчаква ВСИЧКИ; всеки елемент вече носи answer)
Return Script
  - чети dictionary.items
  - push към dictionary.bridge.mainAgentId с bridge.mainSession
  ↓
End
~~~

## 11. Най-краткото правило

Паралелността не се слага в агента, а в graph-а — агентът изпълнява само първия `<SYSTEM CALL>`.
А преди да я сложите, измерете: **фен-аутът плаща време само когато работата по един елемент е
скъпа.** При евтини елементи прави нещата по-бавни и по-скъпи.
